# Design

Migration 8 introduces a singleton configuration control version, immutable request receipts, Projects, reusable Roles and stable Project resources. A configuration command takes the Owner session share lock then the configuration update lock. Check its immutable receipt before expected version, apply one complete Project/Role edit and increment the shared version atomically. A global version keeps the minimum single-Owner editor coherent across selected Role dependencies; it deliberately reports conflicts even for overlapping edits to different entities. GET returns version and current records with optional archived entries included, allowing restore.

POST /v1/owner/configuration/commands accepts schema_version, request_id, expected_control_version, name and payload; GET /v1/owner/configuration and GET .../commands/:request_id provide snapshot/receipt recovery. Project/Role save uses caller-selected stable IDs so retries never create another entity. Bound JSON/collections and reject malformed Unicode. Extend the common JSON Schema and regenerate TS/Go/OpenAPI.

Repository normalization is deterministic and does no network I/O: HTTPS and SSH/scp remotes only, no URL secrets/query/fragment/local paths. GitHub aliases normalize by host and case-insensitive owner/repository; plain Git normalizes transport aliases and .git suffix while retaining path case. Provider verification and opaque repository IDs follow in the next leaf. Remote identity of any recorded resource is immutable; delivery defaults are mutable only for future workspace materialization. Removing a resource marks it inactive after checking existing admitted/succeeded open_workspace operations on unfinished Tasks. Inspection alone does not count as a workspace. No deletion endpoint.

Task project_id is nullable only for existing probe/internal fixtures. initializeTask may take project_id and validates active Project under configuration share lock. Initial Plan publication takes the configuration share lock before Runner/Task locks and verifies every Role belongs to its Project. Configuration edits inspect immutable effective Plan membership while holding the exclusive configuration lock; future start/replan/workspace admission must use the same configuration barrier before Runner/Task locking. Role edits update guidance, never rewrite Plan definitions or launch context. Resource removal conservatively checks the existing operation records; Workspace will own fuller materialization records later.

All migrations are additive and retain earlier checksums; deploy migration before compatible application code. No destructive rollback/down migration: restore app version only if it can safely ignore added records, otherwise restore a reviewed backup. No runtime/process/provider effects occur in this transaction.
